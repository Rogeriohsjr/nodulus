# P13C design: provider rejection remains execution failure

This is a later small test-control design, not dispatch authorization. Root's source review noticed that a JavaScript catch value is tested for truthiness in the graph call loop. A provider can reject with undefined/null/zero/empty string; that must still be an execution failure. It cannot be mistaken for an empty returned response and routed into response correction. Verify actual behavior before claiming RED or changing source.

Use public runWorkflow and a real process-backed provider invocation, with a thin external-provider wrapper that rejects with an explicit falsy value after its actual child result. Give the profile responseRepair and a repair hook that records any call; expect PROVIDER_FAILURE, no response repair, no accepted artifact and no dependent launch. A companion valid initial error outcome, with the same repair capability, retains its original error and also requests no correction. Preserve provider actions and original launch evidence; do not conflate these boundary errors with required storage failure. Only the external provider behavior is replaced; core/storage/process modules remain real.

Keep this control small and independent of the optional measurement cases. A bounded correction, if needed after accepted RED, uses an explicit caught-error flag or equivalent tagged result, without changing the safe two-repair budget or legacy execution. Keep non-string provider return handling typed and fail-closed as well. No test timeouts or provider actions are repeated to obtain GREEN.
