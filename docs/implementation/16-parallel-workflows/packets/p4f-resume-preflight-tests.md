## Source-backed behavior and contract boundary

`resumeWorkflow` in `src/application/resume-workflow.ts` acquires the run lock before `resumeWorkflowLocked` (lines 170–194). A running checkpoint fails `RUN_RECOVERY_REQUIRED` (191); a graph checkpoint with `schemaVersion === 2` enters `resumeGraphAnswerLocked` (194). That graph path verifies captured context shape and workflow (331), then `verifyCapturedGraphFiles`, live workspace references and `verifyGraphResumeLedger` (353–360) before it parses/commits the supplied answer. The ledger binds pending request and committed answer hashes (`src/core/graph-resume-evidence.ts:145,184`), event evidence, saved call/attempt evidence and accepted node result/validation/response/artifact hashes (256–309). These branches precede provider use and answer mutation.

The graph-specific version guard currently reports `RUN_STATE_INVALID` for captured definition/schema/engine mismatch. The version-1 branch in the same application has dedicated `RUN_SCHEMA_UNSUPPORTED` and `ENGINE_VERSION_UNSUPPORTED` codes; those codes are not currently used by the graph-specific guard. A checkpoint `schemaVersion` other than `2` also falls through to the version-1 branch, so the test should record the observed fail-closed behavior without claiming that the discriminator is explicitly recognized as an unsupported graph version.

`resumeGraphAnswerLocked` calls `writer.recordAnswer` and returns `needs_input` immediately when another request remains; it does not call provider methods (lines 379–413). When the last answer arrives it calls `writer.recordFinalAnswer` first, then starts `executeGraphWorkflow` (383–396). Per `src/core/graph-node-runner.ts:114,239`, captured-profile availability runs inside that normal scheduler slot. A false result is raised as `PROVIDER_UNAVAILABLE`; `src/adapters/providers/default-provider-port.ts:161` returns false when the captured profile is disabled or its executable cannot be started. The graph path does not call legacy `validateSavedProviderAvailability` (resume-workflow.ts:240,449) before answer mutation, and the accepted P4B2b packet explicitly says not to add eager duplicate availability probes. Therefore the provider-unavailable row characterizes current post-answer execution; it is not a no-write compatibility-preflight test. If the product contract is changed to require unavailable-provider rejection before answer mutation, that needs a separate contract/source decision and test-first packet.

The frozen contract in `runtime-contract.md` requires version, saved-artifact and workspace-reference compatibility before answer mutation or provider probes, preservation of captured profiles, and fail-closed corrupt state. It does not promise that final provider availability is checked before the final answer commit. Existing `CAPTURED_PROVIDER_UNAVAILABLE` examples in `ask-005-captured-context-guards.test.ts` exercise the version-1 workflow and should not be copied as graph error-code evidence. P4C lock, stale-lock and crash packets remain separate.
