# P4 preparation: request-bound graph continuation

This is source-backed design. P3's exact d9c2de8 head completed local and hosted acceptance; Root created codex/parallel-04-recovery from it and dispatched only P4A's two test files. Runtime implementation still requires their observed RED and review. Root and Sol reviewed Main Luna's resume audit against runtime-contract.md, public resumeWorkflow, ProviderInvocation and buildPrompt. No successful graph resume or additional scenario result is claimed.

Existing blockers: resumeWorkflowLocked reads version1 pending/request.json and rejects schema2; graph needs an early schema2 dispatch under the existing run lock. Graph status also follows the legacy single-request path. executeGraphWorkflow starts accepted/pending sets empty, so invoking it afresh would replay roots. runGraphNode currently builds empty prompt answers and has no initial continuation parent. Those are future test-first changes, not permission to bypass running/uncertain safety.

Freeze node-answer delivery as a new continuation invoke for a previously completed needs_input node: new runtime callId and next attempt, operation invoke, parentCallId equal to the verified completed question call. Rehydrate its exact request and committed answer hashes and pass only that node's validated answers in BOTH buildPrompt and ProviderInvocation.answers. Retain old completed call/evidence and any previous committed answers for that node. This follows the existing legacy answer-prompt mechanism; it does not promise provider-session continuity or permit replay of accepted or possibly active work.

Caller-input requests remain distinct: kind caller_inputs, null node identity. Their final valid answer makes eligible roots schedulable; it does not create a fictional node continuation or artifact. Keep inputs.json immutable. Derive effective caller values from captured intake plus hash-bound committed answers and compare that with checkpoint projections before scheduling.

One requestId is answered per locked operation. Verify schema/version, run state, exact pending ID, captured request/answer contract, workspace references and prior evidence BEFORE mutation. A valid partial answer writes the answer/event then checkpoint last and launches nothing while any question remains unanswered. The final answer restores accepted artifacts from exact canonical refs/hashes and schedules only eligible answered pending or not_started nodes. Missing, orphan, corrupt or contradictory answer state cannot authorize a call. Terminal errors/active or uncertain runs fail closed.

P4 packets should first prove terminal-error precedence and immediate durable pending diagnostics during sibling drain, then multi-node questions and exact partial/final answer behavior, then fresh-process restore/lock/version/evidence failure controls, ordered history and crash windows, and caller-input pauses/reference drift. A draining sibling error retains question IDs diagnostically but cannot be resumed by answering them. Accepted siblings retain exact bytes/call identities and are never invoked again. Restore prior metrics/events through the single writer without overwriting earlier history.

Concrete test/source ownership, observed REDs, frozen hashes, deadlines and review gates are assigned only after P3 acceptance. Existing real storage, process fixtures and run lock may be reused; no private adapter substitution, fabricated IO, live inference or unreviewed replay policy is authorized by this design note.
