## Execution preparation

Each C3 attempt begins at the INITIAL two-question pause: both A and B are unanswered, neither has a checkpoint answer ref/hash, and A's target answer file is absent. The gated child performs the FIRST A answer while B remains unanswered. Do not reuse F's post-A-partial fixture state; F separately injects B's orphan after a committed A answer. A pre-existing A target is setup failure before watcher/gate release. Answering B last instead would allow provider dispatch on a missed window and is outside this feasibility design.

Read-only inspection confirmed that the frozen PAR033 driver takes six arguments (operation, nonce, project root, run ID, request ID and answer file), awaits its public operation and delegated settlements at module top level, and prints one bounded envelope. A separate owned Node wrapper can use exactly that argument tuple, wait at an external pre-API gate, await-import the unchanged driver, write an import-completed marker and hold an external exit gate. The wrapper and imported driver remain one actual process/PID. No runtime/storage function or argv replacement is needed. The post-import marker means the API settled; it cannot create or prove a pre-checkpoint window.

The proposed feasibility controller is an isolated QA artifact under the ignored checkpoint folder, with an explicit Vitest include/config so it does not enter ordinary scenario discovery. It may reuse real project helpers, the unchanged PAR031 provider and native pin fixture, and the unchanged PAR033 driver. It is not a deterministic CI scenario or new product command. Root must inspect the actual controller/wrapper and Sol must review the stable native protocol before any experiment. Record each attempt explicitly as captured or a concrete setup miss. An advanced checkpoint, expected partial API return/released lock, unsupported watcher or lost identity cannot count as captured or behavioral RED. An unexpected API error is a control failure requiring diagnosis, not a generic timing miss. A genuine captured window requires valid bare answer bytes, the byte-identical old checkpoint without its answer ref and the genuine stale owner lock. Fresh RUN_RECOVERY_REQUIRED then proves the stale-lock guard; the independent F orphan-file case proves fail-closed saved-answer inspection without that lock. Keep those proof boundaries distinct.
