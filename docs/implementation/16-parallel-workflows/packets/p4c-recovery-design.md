# P4C/D preparation: fresh processes and fail-closed evidence

Planning only. P3 remains gated; P4A and answer-continuation acceptance precede these tests. A read-only Luna audit identified existing production patterns: ASK002 uses runFreshWorkflowDriver from tests/support/clarification-resume.ts and actual dist/index.js in separate Node processes; SAFE004 uses competing real resume processes and an actual exclusive lock; SAFE006 kills an owned runner after actual provider entry. ASK005 and FB045 mutate saved quiescent evidence as external corruption. These are reusable patterns, not graph acceptance evidence.

Split the future work into small packets:

- Fresh final resume in an independent Node process restores accepted seed refs/bytes/call IDs, continues only answered pending nodes, and preserves ordered prior events/metrics. Rebuild real dist before child-process RED/GREEN checks.
- Real interrupted continuation: hold the actual provider child, observe running/active launch evidence, kill only the owned runner, then prove recovery-required and no new provider entry or accepted seed changes. Preserve/release/drain every known fixture PID. A manually edited checkpoint is a separate corruption control and must not be called a crash experiment.
- Real lock contention: one resume process holds the run lock while its provider is held; a second process rejects RUN_LOCKED without changing files or dispatching. A dead-PID stale lock rejects RUN_RECOVERY_REQUIRED and remains intact. Local storage uses exclusive .resume.lock with pid/token; runtime does not auto-delete stale evidence.
- Independent post-pause corruption controls: canonical request ref/hash/identity and answer contract; orphan/mismatched/contradictory committed answers; event sequence/history; accepted result/validation/response/artifact identity/hash; schema/engine and captured definitions/inputs/references; external workspace reference and captured executable availability. Each uses a fresh real pause, zero subsequent probe/inference and byte-identical run files after rejection. Do not overwrite the original failure with repair or adopt current profiles/instructions.
- Actual answer commit crash: observe a genuine physical answer write before checkpoint publication in an owned child, interrupt at that boundary, and prove the orphan answer cannot authorize continuation. Choose the concrete boundary against the implemented writer; do not replace internal storage behavior or label static corruption as observed write ordering. Thin storage observers must delegate real outcomes unchanged.

Existing error names: RUN_LOCKED for a live/unreadable owner; RUN_RECOVERY_REQUIRED for stale lock/running/incomplete provider work; RUN_STATE_INVALID for saved evidence/hash contradictions; RUN_SCHEMA_UNSUPPORTED, ENGINE_VERSION_UNSUPPORTED, WORKSPACE_REFERENCE_CHANGED, CAPTURED_PROVIDER_UNAVAILABLE, PENDING_REQUEST_MISMATCH and ANSWERS_INVALID for their specific guards. The legacy checkpoint-read wrapper currently uses RUN_NOT_FOUND for missing/bad checkpoint JSON. Freeze graph-specific mappings from actual implementation before assertions; do not invent current support.

Root dispatches exact files/ownership, deadlines and cleanup after prerequisites. Source/tests remain unwritten. Every real crash, corruption control, ordinary fresh process, local gate and hosted check must keep separate evidence.
