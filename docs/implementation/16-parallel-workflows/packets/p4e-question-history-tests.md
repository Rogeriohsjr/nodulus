## Case 1: accepted node between question waves

Use the unchanged PAR031 fixture with a serial dependency chain `seed -> A -> B`, one output alias per declared result, and the existing distinct A/B answer contracts. Keep declaration order explicit and make B's mapped input a transitive ancestor artifact. The provider fixture already emits seed success, A attempt 1 question / attempt 2 success, and B attempt 1 question / attempt 2 success. Configure each real fixture process with an owned barrier and verify its saved request identity before release.

1. Run through the public API. Require seed's valid artifact to be accepted, then A attempt 1 to produce a runtime-owned question. Record A's runtime UUID, question call/attempt, exact pending request/result/validation/raw-response bytes and hashes, captured inputs, events, metrics, and accepted seed evidence.
2. Answer A with its valid contract. A attempt 2 must run once with a new call ID, parentCallId equal to A attempt 1's question call, and exactly A's answer. Require A's valid artifact acceptance before B starts. B attempt 1 then emits its real question. The public pause contains only unanswered B; `result.request` aliases B. Capture the now-accepted A state and exact B request evidence.
3. Answer B. Require success, A attempt 1/2 and B attempt 1/2 exactly once, seed exactly once, no replay of accepted seed or A, and no extra provider probes/invokes. The final outputs use declared aliases/order. Preserve the earlier A question, A answer file and `request.answered` event as immutable history; B's answer is independently bound to its own runtime request. Require A/B prompt and structured invocation answers to match their respective values, call parents to match each node's preceding question call, and inputs.json remain byte-identical.
4. Preserve old event and metric prefixes; require unique contiguous appended event sequences beginning at the saved `graph.nextEventSequence`, and exactly the expected new call-keyed metrics/call evidence. Recheck every retained request, answer, result, validation, response and accepted-artifact ref/hash in the final run. Require no provider action when validating a mismatched ID or invalid answer, if those controls are included; those controls must leave the entire run tree unchanged.

The history verifier must validate A's answered question against its original immutable request/call/attempt evidence even though A is now accepted at attempt 2. It must not require the old A request to match A's current checkpoint call. The latest pause wave is B only: exclude answered A history because A is accepted, while preserving A in the ledger. The public outstanding-request projection contains only unanswered B.

## Case 2: one node asks twice and carries answers forward

Use a separate graph with a real `seed -> A` dependency. The dedicated fixture returns a valid seed artifact; A attempt 1 asks for key `first`, A attempt 2 asks for a second question with a distinct key `second`, and A attempt 3 returns a valid artifact only when it receives both answers. Use distinct keys so cumulative answer delivery is directly observable; do not make key-collision/overwrite behavior an acceptance assertion in this packet.

1. Pause on A attempt 1 and record runtime request UUID A1, exact request/attempt/call evidence, accepted seed, and event/metric/input snapshots. Answer A1. Require one A attempt 2 with parentCallId=A1's call, a fresh call ID and only `{first: ...}` in both the actual prompt's answer section and structured invocation.
2. A attempt 2 emits a second valid needs_input result. Require a distinct runtime UUID A2, attempt 2/call identity, exact saved pending evidence, and a pause event whose requestIds describe this current wave `[A2]`. A1 remains in the checkpoint ledger as answered history, but is not an outstanding request or member of the current pause wave. The returned `result.requests` contains only A2 and `result.request` aliases it.
3. Answer A2. Require A attempt 3 exactly once with parentCallId=A2's question call, fresh call ID, and merged own-node answers `{first: ..., second: ...}` in both structured invocation and the real prompt. Require success, the exact output alias, unchanged accepted seed/input evidence, and all three A attempts plus both question/answer histories retained and hash-valid. There must be no seed replay or extra provider operation.

Question IDs are request-scoped; the distinct answer keys avoid depending on collision policy. Existing version-1 resume currently merges answer objects with later keys winning on collisions. Before any graph implementation relies on that behavior, Root/Sol must decide whether graph questions with duplicate answer keys are rejected or follow the same last-answer-wins rule; record that decision separately and add a focused case only if the contract requires one.

If current behavior already passes either case, record that case as characterization and do not break it to manufacture RED. Freeze both hashes and the exact results for Root/Sol review before any source edits; implementation needs a separate narrow dispatch.

Source-backed verifier gaps at packet preparation: `verifyGraphResumeLedger` requires every pending entry's node state to be `pending` at that entry's attempt/call, rejects a second request for the same node, and rejects a node that is both accepted and present in the historical pending ledger. Its `answersByNode.set(nodeId, answer)` overwrites earlier answers instead of merging distinct committed answer objects. Finally, it compares the last `run.needs_input.requestIds` to all ledger request IDs in declaration order. That is incorrect for both accepted prior waves and repeated requests: derive the current pause wave from node states that are currently pending and the matching question call/attempt, including answered requests whose node remains pending on that same question; exclude answered requests for nodes now accepted. Historical request/answer evidence must still be verified. Keep the public outstanding projection filtered to unanswered requests only. These are implementation hypotheses backed by current source; the packet's run must establish the actual observed behavior.
