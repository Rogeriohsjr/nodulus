## Four cases

1. Three independent nodes alpha/beta/gamma, concurrency two, explicit empty resources. Start alpha/beta build children before either is released. Release beta build with malformed final Nodulus JSON and wait until its actual adapter promise has settled, holding delivery at the external boundary. Then release alpha build similarly. Once both real adapter results are available, deliver both raw results in one controlled promise wave. Record the exact original call IDs; this exercises concurrent metric publication, rather than just concurrent CLI exit. Both response-only repairs must start with their own first session IDs, distinct from the other node's ID. Hold alpha repair one. Beta repair one remains malformed; beta repair two must use beta's original session and full-invocation attempt, with increasing call attempts and correct parent IDs. Release beta repair two valid: beta is durably accepted and gamma may start while alpha repair is held. Gamma's provider-entry checkpoint shows beta accepted and alpha active. Freeze beta evidence hashes. Complete gamma and alpha, then assert all declared aliases, six unique calls (alpha two, beta three, gamma one), exact per-call usage/operation/parent identity and unchanged beta evidence. Every node has one build/action; every correction uses `--agent nodulus-response` and its own `--session`. Do not assert provider-entry order. Slot and evidence ordering use saved checkpoints.
2. A schema-invalid success artifact is corrected once through the actual response-only adapter; its final artifact validates and the original build/action is not repeated.
3. A schema-valid artifact rejected by a real executable validator is corrected once; the validator runs against the corrected artifact and accepts it. The fixture validator returns exact verdicts and records its two inputs/PID. No action replay or fabricated fallback.
4. A response remains malformed through two response-only corrections. Return REPAIR_EXHAUSTED, accept no artifact and launch no dependent. There are exactly one build and two correction calls, each isolated and parent-linked; never a third correction or another action.

For simple cases pre-release the known fixture barriers and assert the returned outcome directly. For the concurrent case, waiting for a missing repair must also observe a settled workflow or saved terminal node/run error, so unsupported repair produces an immediate meaningful failure rather than only a 10-second marker timeout. A recurring uncommitted checkpoint event remains a separate failure to diagnose with the existing evidence.

## Explicit P12 fault-test staging

Per-call completion/metric publication belongs immediately after an actual invoke/repair returns and before executable validation. The original cap-one fault cases assumed no call-completion checkpoint could exist between provider start and later artifact persistence. Preserve their failed-publication invariant while moving their injection to a stable later boundary:

- Copy the unchanged real P11 barrier validator into alpha for both P12 fault cases. Release alpha's provider, then wait for its validator's started marker.
- Assert alpha's provider.call.completed event exists and is committed (`checkpoint.graph.nextEventSequence` is greater than that event's sequence) before installing a blocker. This is a new required per-call ordering assertion; the old P12 runner may fail it immediately before P13 is implemented. Do not wait for a missing event until the held validator times out. A started validator alone does not prove publication.
- Snapshot the last committed checkpoint at that point, require result.json still absent, install the existing run.json or result.json directory blocker, and release the validator. Retain checkpoint equality, original filesystem diagnostics, orphan valid result, no later admission, public fail-closed resume and no-probe/no-write assertions.
- Await the validator PID exiting before deleting generated paths. Retain all existing P12 time bounds. Record the intentional staging hash transition and actual RED; no original failure assertion may be removed.
