# P4C2 real lock and runner-crash preparation

Read-only preparation from committed 84190d2. Exact scenario IDs follow scenarios.md: PAR-033 fresh-process restore, PAR-034 locks/incompatible state, PAR-035 event history and PAR-036 cancellation/crash windows. Names/ownership are not dispatched here.

The initial schema2 run currently acquires no .resume.lock. Public resumeWorkflow acquires it before checkpoint reads. LocalIntakeStorage.acquireRunLock uses exclusive open(wx); a live or unreadable owner yields RUN_LOCKED, a dead owner RUN_RECOVERY_REQUIRED, with no automatic lock deletion. Test real ownership from an already paused graph; do not claim current initial-run locking. A killed initial graph runner leaves running/active checkpoint state, which also requires recovery before provider work.

SAFE004 and tests/support/recovery-scenarios.ts show real child/file-wait patterns, but recovery-resume-driver.mjs supplies a synthetic provider and proves v1 behavior. workflow-driver.mjs also bypasses the default adapter. Prefer the future frozen PAR033 real-default driver at its tracked path; a hold-lock mode may import LocalIntakeStorage from ../../dist/adapters/storage/local-intake-storage.js and use its real acquireRunLock(projectRoot,runId). New driver changes must include the prior fresh-process control under the new hash.

The lock case creates a real paused graph with actual default CLI fixtures, then starts an owned Node lock holder. Require PID/token-ready evidence only after actual acquisition. A separate fresh resume must reject RUN_LOCKED with identical run/lock bytes and no provider/fixture activity. Terminate the still-live owned holder through its retained ChildProcess handle, await close/native exit, and prove the exact lock bytes remain. Another fresh resume must reject RUN_RECOVERY_REQUIRED with no deletion/mutation/dispatch. Do not forge a lock file or target arbitrary PID numbers.

The crash case runs seed -> held node in an owned fresh runner process. Require durable accepted seed refs/hashes, running/active child checkpoint and an actual live CLI marker matching node/call/run before killing the runner through its owned handle. After close, release and drain the exact held fixture child; successful exit metadata is not assumed after its parent died. Fresh public resume must require recovery without new readiness/inference, seed replay or checkpoint/accepted-evidence mutation. Distinguish real process death from editing state JSON.

Keep an absolute 20s scenario deadline, one shared 10s cleanup deadline and 35s case ceiling, plus the established fixture watchdog. Track every driver/holder/provider operation and native identity, release gates before drain, and retain failed/uncertain projects. First GREEN is honest characterization, not invented RED. A genuine answer-file-before-checkpoint crash window needs its own observed native setup and remains excluded here; a denied write or synthetic orphan file does not establish that crash window.

For the stale lock-owner control, retain the owned native identity handle through the fresh resume assertion. On Windows the existing pinned native process-handle pattern prevents the terminated owner's numeric PID from being recycled before storage checks it; release the pin only during final owned cleanup. The stale-lock rejection establishes lock behavior, rather than inspection of later saved-state evidence. Do not target a historical numeric PID or silently treat a reused identity as the original owner.
