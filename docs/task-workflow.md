# Plan small tasks, then implement a selected packet

The reusable local-Qwen workflows produce a junior developer handoff and execute a selected, reviewed packet. They support explicit repository ownership and ordered dependencies. They are supervised workflows: a valid plan is not proof that its requirements are complete, and Qwen review does not replace factual review.

## Setup

Use Node 24, OpenCode and Ollama in a dedicated worktree. This feature must be present in your installed Nodulus version. In this source checkout, replace `nodulus-task` with `node scripts/task-workflow/cli.mjs` and `nodulus` with `node dist/bin.js` after building.

```sh
nodulus-task setup .
```

Setup installs `task-plan`, `task-implement` and `task-document` definitions, contracts, instructions and validator helpers under `.nodulus`. It creates `opencode.json` only when absent. Existing settings and provider profiles are preserved; differing workflow/helper files cause setup to stop. Inspect an existing OpenCode configuration before a live run: both `model` and `small_model` must use the desired local provider, its endpoint must be `http://127.0.0.1:11434/v1`, and the build agent must deny tools. The supplied example enables only Ollama and uses `ollama/qwen-nodulus-coder:latest`. That alias must already exist locally; setup does not download a model. Adjust the OpenCode model and `.nodulus/settings.json` together if using another installed model. Verify with `ollama list` and `nodulus doctor --json` before inference.

## Prepare repository context

Create a manifest using the shape below. `root` is an absolute path. Paths under `files` are relative POSIX paths; include intended new files, the frozen test, supporting source references and documentation. Add a separate repository entry for each checkout. Commands are trusted configuration supplied by the operator, never generated by the model.

```json
{
  "limits": { "maxFiles": 3, "maxCases": 3 },
  "repositories": [{
    "id": "app",
    "root": "/absolute/path/to/worktree",
    "files": ["src/example.ts", "tests/example.test.ts", "docs/change.md"],
    "checks": [{
      "id": "focused",
      "executable": "node",
      "args": ["node_modules/vitest/vitest.mjs", "run", "tests/example.test.ts"],
      "redContains": "exact assertion for the missing behavior"
    }]
  }]
}
```

Use Node script commands with argument arrays on Windows/macOS/Linux. Checks run without a shell, with a maximum 120-second timeout and bounded output. Add repository-specific lint/typecheck checks as well as the scenario check. The RED command is the selected check containing `redContains`; the other checks must pass after implementation. A trusted check can execute code, so inspect scripts and use a disposable worktree. This is not a security sandbox.

```sh
nodulus-task prepare repositories.json .
nodulus run --workflow task-plan --inputs-file .nodulus/task-plan-inputs.json --request-file task.md --json > plan-result.json
```

Preparation captures hashes and source contents, rejecting symlinks, escaping paths and more than 24,000 source characters. It never silently truncates. Supply focused context and replan when requirements or sources change. Templates are distributed under `examples/task-planning` in the package.

## Read the plan

The output contains `ready` (one task), `split` (two or more tasks), or `blocked` (questions, no invented tasks). A successful Nodulus outcome can contain a blocked plan; inspect `decision` before execution.

Each packet names the repository, goal, one primary file and symbol, source references, dependency IDs, Given/When/Then acceptance, one test file and expected failure, fixed check IDs and one documentation file. Dependencies must appear earlier, including dependencies across repositories. Unknown sources/checks and oversized packets are rejected. Symbol validation checks literal source presence, not semantic API correctness; review the proposed calls and assertions.

The current executor is deliberately small: one primary file, one frozen test and one documentation file per runtime packet. Split larger changes into independently meaningful behaviors; do not split merely to conceal a coupled change. If that cannot be done safely, keep the task blocked for a larger executor/manual implementation. Increasing `maxFiles` does not remove this executor limit.

## Approve the test and select a packet

Write/review the real scenario test first, exercising production entry points and mocking only external services. Test generation is a separate supervised step in this version. Compute its SHA-256 after review:

```sh
node -e "console.log(require('node:crypto').createHash('sha256').update(require('node:fs').readFileSync('tests/example.test.ts')).digest('hex'))"
nodulus-task select plan-result.json T1 . REVIEWED_TEST_SHA256
```

Passing the hash is your approval of that exact test. Selection checks the plan again, verifies current source/dependency hashes, checks the approved test hash, then runs the trusted RED command. Exit 1 plus the configured assertion text is required. Inspect the receipt: a poorly chosen substring cannot prove a meaningful behavioral failure. Syntax/import/runner failures are not RED. The test is frozen thereafter.

Selection refuses unfinished executions. Dependencies require accepted receipts bound to the same context, repository and exact dependency task definition. Execute packets in dependency order. Receipts are local trusted evidence, not signed attestations; do not edit or share them as an authorization mechanism. Repreparing changes the context identity, so previous receipts cannot automatically authorize a new plan.

## Execute and inspect

```sh
nodulus run --workflow task-implement --inputs-file .nodulus/task-implement-inputs.json --request-file task.md --json > implementation-result.json
```

The nodes are **Qwen implementation → apply and checks → Qwen documentation → apply and checks → Qwen review**. The models produce artifacts with tools denied. Validators perform confined, stale-base-checked single-file replacement, run fixed checks, verify frozen hashes and stop on failure. A reviewer requesting changes prevents a completion receipt. Perform independent final review and the repository's full quality gate before commit/PR.

For a documentation-only packet, selection reports `task-document`: use that workflow instead. It runs documentation → checks → review, editing one Markdown file once. Its primary file and documentation path must be the same.

| Work | Test strategy |
| --- | --- |
| Runtime or install/upgrade behavior | Real scenario RED/GREEN; existing upgrade/archive fixtures where applicable |
| Documentation only | Explicit `non-tdd` reason; concrete link/content/render checks and factual review |
| Hosted pipeline configuration | Explicit item-specific exception; static checks plus actual hosted evidence before claiming hosted success |
| Descriptive package metadata | Explicit exception, manifest/archive checks; runtime packaging changes still require TDD |

All exceptions need trusted replacement check IDs. A generic command such as `node --version` is only a fixture example, not adequate validation of real documentation or pipelines. No workflow publishes, merges, upgrades software or grants credentials on your behalf.

## Evidence and recovery

- `.nodulus/runs/<runId>/`: prompts, raw responses, validation, transport and available provider usage.
- `.nodulus/task-context.json`: captured repository context; may contain private source.
- `.nodulus/task-execution.json`: selected task, frozen hashes and accepted phases.
- `.nodulus/task-receipts/<executionId>/`: RED, apply attempts and check stdout/stderr/exit status.
- `.nodulus/task-completed/<contextHash>/<taskId>.json`: accepted review, exact task hash and final captured file hashes.

Keep these local files out of commits; publish sanitized reports separately. The workflow stops on a rejected artifact and does not automatically rerun a completed code phase. Failed checks can leave the proposed file in the worktree for inspection.

After accepted code or documentation, prepare one bounded recovery using the installed helper:

```sh
node .nodulus/task-tools/runtime.mjs recover .
nodulus run --workflow task-recover --inputs-file .nodulus/task-recover-inputs.json --request-file correction.md --json
```

Write `correction.md` with the exact rejected phase's error and required correction. Preparation verifies accepted artifact/check digests and frozen files, reruns the trusted checks, refreshes captured source, then generates only the remaining nodes. Accepted code resumes at documentation; accepted code and documentation resume at review. A documentation-only task resumes at review. The generated workflow never includes the accepted code node.

Only one recovery preparation is allowed per selected execution. Missing legacy evidence, changed files/receipts, failing checks, completed executions and unsupported phase order are rejected. This requires the updated helper set from setup: `io.mjs`, `runtime.mjs`, `recovery.mjs` and `recovery-state.mjs`. Setup refuses differing existing helpers; preserve old executions and use a fresh worktree for the updated setup. It does not reconstruct evidence for older executions or silently overwrite helpers.

Do not delete state and blindly replay implementation. The preparation bound is not an inference budget: manually relaunching a generated workflow is still operator-controlled, and completed-phase validators reject replay. There is no multi-file rollback, whole-workflow token budget, concurrency lock or automatic multi-packet scheduler. Use one execution at a time in a dedicated checkout, preserve unfinished work, and obtain strong review at a stable checkpoint.

The planning pilot report in the repository records both successes and coordinator interventions. A local provider's reported zero dollar cost excludes electricity and separate coordinator/reviewer account usage.

## Bounded review revisions

After preparing a runtime packet, reviewing/freezing its scenario test, observing RED and selecting it, run:

```sh
nodulus-task loop /path/to/project 1
nodulus-task loop-status /path/to/project
```

The final argument is the maximum corrections, 0–2, in addition to the initial iteration. Each iteration invokes configured packet-code, packet-docs and packet-review profiles through separate Nodulus runs. A valid changes_required review sends its exact summary and current source back to the developer. New code requires fresh executable checks, documentation and review. There is one code file and one document per iteration; tests and captured reference files remain frozen. Completion requires acceptance and cannot overwrite an existing task/context receipt. Exit 0 means accepted; exhaustion or error exits 1.

Each phase has a regular .nodulus/runs/<runId> record. Controller requests/responses and transitions are in .nodulus/task-loops/<origin>, with run IDs linking the two. Rejected iterations keep their task-receipts directories. Generated single-node definitions remain available for inspection. Nodulus checks schemas; the controller owns application/checks exactly once. Model summaries are not executable proof.

This initial loop supports fresh selected runtime TDD tasks. Failed checks, malformed responses and unsafe changes stop with evidence. Automatic failed-check revision and crash continuation are not implemented. loop-status is read-only and shows the journal and lock without inference. A lock may belong to a live or interrupted process; inspect the process, file hashes, checks and receipts before manual recovery. Never remove a live lock or reset execution state to force replay. Use an isolated checkout and one task executor. Terminal reentry does not schedule new inference.

Provider choice remains in project configuration. Local Qwen is optional, and the product does not hard-code a model or require a proxy. Disabling title generation and automatic compaction helped the measured OpenCode artifact-only experiment, but may be inappropriate for long interactive sessions. A correction cap is not a hard token cap; provider-internal subcalls can add usage.
